# Правила изменения Liquibase-миграций

Этот файл обязателен к прочтению перед созданием, редактированием, удалением, переименованием или перемещением файлов в `src/main/resources/db/changelog`.

## Неизменяемость опубликованных changeSet

- Migration-файл, существующий в `HEAD`, считается опубликованным и неизменяемым. Не редактируй его содержимое, не форматируй, не удаляй, не переименовывай и не перемещай.
- Перед изменением конкретного файла проверь его наличие в `HEAD`:

```bash
git cat-file -e HEAD:src/main/resources/db/changelog/changes/NNN-name.yaml
```

- Exit code `0` означает, что файл менять нельзя. Создай новый файл со следующим свободным номером и отдельным уникальным `changeSet.id`.
- Отсутствующий в `HEAD` новый migration-файл можно исправлять до первого commit. Наличие файла только в index или working tree не делает его опубликованным.
- Не используй `runOnChange`, `runAlways` или `clearCheckSums`, чтобы обходить checksum mismatch для изменения структуры production-базы.

## Создание новой миграции

1. Найди максимальный номер в `src/main/resources/db/changelog/changes` и выбери следующий свободный номер.
2. Создай новый YAML-файл с уникальным `changeSet.id`.
3. Подключи файл в конце `src/main/resources/db/changelog/db.changelog-master.yaml`.
4. Пиши изменение так, чтобы оно применялось поверх схемы, созданной всеми предыдущими changeSet. Не переноси новое изменение назад в старый файл.
5. Для изменения существующей таблицы используй новый `ALTER TABLE` или штатные Liquibase changes, а не редактирование исходного `CREATE TABLE`.

## Обязательная проверка

После любых изменений схемы запусти:

```bash
.agent/rules/check-liquibase-migrations.sh
./gradlew test
```

Первая команда должна выполняться также перед завершением задачи, даже если migration-файлы менялись косвенно. Если она сообщает об изменённой существующей миграции, восстанови файл из `HEAD` через осознанную правку и перенеси изменение в новый changeSet. Не очищай checksum и не изменяй `DATABASECHANGELOG`.

Тесты миграций выполняются на PostgreSQL через Testcontainers. Успешное применение на новой пустой базе дополняет, но не заменяет проверку неизменности файлов из `HEAD`.
