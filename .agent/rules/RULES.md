# Правила разработки `Tovarika`

## 1. Контекст проекта

`Tovarika` — backend-сервис платформы для создания карточек товаров для маркетплейсов. Сервис отвечает за пользователей и авторизацию, товары и их анализ, проекты, шаблоны, генерацию и редактирование карточек, файлы, экспорт и биллинг.

Проект находится на ранней стадии: сейчас реализованы инфраструктурный каркас, подключение PostgreSQL, Liquibase, MinIO, генерация API-кода и развертывание. Не считай endpoint готовым, пока для сгенерированного интерфейса нет реализации и прикладной логики.

## 2. Технологии

- Java 21, Spring Boot 4 и Gradle Wrapper;
- Spring MVC, Validation и Spring Data JPA;
- Spring Security OAuth2 Resource Server, short-lived JWT access tokens и Backend-managed opaque refresh sessions;
- PostgreSQL и Liquibase;
- MinIO как S3-совместимое хранилище изображений;
- OpenAPI Generator и springdoc/Swagger UI;
- Docker и Docker Compose.

Новые библиотеки добавляй только при реальной необходимости. Версии зависимостей меняй отдельно от функциональных задач, если обновление не требуется для самой задачи.

## 3. Архитектура и структура кода

Проект развивается как модульный монолит. Новый бизнес-код группируй по функциональным модулям: `auth`, `users`, `billing`, `products`, `projects`, `templates`, `cards`, `assets`, `jobs`, `exports` и другим областям из API-контракта.

Внутри модуля разделяй ответственность:

- `api` — REST-контроллеры, входная валидация и преобразование DTO;
- `application` — сценарии использования, транзакции и координация портов;
- `domain` — бизнес-модели и правила без зависимости от Spring, JPA, MinIO и transport DTO;
- `infrastructure` — JPA-репозитории, внешние клиенты и реализации портов.

Зависимости направлены от `api` к `application` и `domain`. Инфраструктура реализует объявленные внутри приложения порты. Контроллеры не обращаются напрямую к JPA-репозиториям, MinIO и внешним API. Общий код выноси в `shared` или корневой `infrastructure` только при реальном использовании несколькими модулями.

## 4. API-контракт

- Единственный источник истины API — соседний репозиторий `tovarika-api-contract`.
- Изменение endpoint, DTO, статуса ответа или схемы ошибки сначала вносится в контракт.
- Публичный и provider-контракты берутся из `dist/openapi.yaml` и `dist/provider-openapi.yaml`.
- Код в `build/generated/openapi` не редактируется и не коммитится.
- Контроллер реализует интерфейс из `com.tovarika.api.publicapi` или `com.tovarika.api.provider`.
- Сгенерированные DTO используются только на границе API; доменные сущности и JPA-модели наружу не возвращаются.
- Формат ошибок, авторизация и обязательность полей должны соответствовать контракту.

Если контракт изменился, сначала собери его командой `(cd ../tovarika-api-contract && npm ci && npm run build)`, затем перегенерируй Java-интерфейсы.

## 5. Данные и транзакции

- Схема PostgreSQL изменяется только через новый changeset в `src/main/resources/db/changelog/changes`.
- Уже применённые changeset-файлы не переписывай; добавляй следующий файл и подключай его в master changelog.
- `spring.jpa.hibernate.ddl-auto=validate` сохраняется: Hibernate не должен создавать production-схему.
- Границы транзакций задавай в application-сервисах, а не в контроллерах.
- Не отдавай JPA-сущности через REST и не связывай доменную модель с ленивой загрузкой.
- В PostgreSQL храни метаданные файла и object key; бинарные изображения принадлежат MinIO.

## 6. Внешние интеграции

- Работа с MinIO выполняется через инфраструктурный сервис или порт, а не напрямую из контроллера и домена.
- Object key создаётся сервером; пользовательский путь или имя файла нельзя принимать как готовый ключ без нормализации.
- Ошибки MinIO и других провайдеров преобразуются в ошибки приложения и не раскрывают внутренние детали клиенту.
- AI-провайдеры, платежи и другие внешние сервисы подключаются через интерфейсы и отдельные адаптеры.
- Входящие платежные webhook должны проверять подлинность и обрабатываться идемпотентно.

## 7. Конфигурация и безопасность

- Настройки читаются через типизированные `@ConfigurationProperties`; связанные значения не размазывай по `@Value`.
- Локальные значения по умолчанию допустимы в `application.properties`, production-секреты передаются только через окружение.
- Не коммить пароли, токены, приватные ключи и production `.env`.
- Не записывай в логи пароли, access/refresh-токены, cookies, платежные данные и содержимое пользовательских файлов.
- Входные данные проверяй на границе API и повторно защищай критичные бизнес-ограничения в application/domain.
- Проверка владельца ресурса и прав доступа выполняется на сервере для каждого защищённого сценария.

## 8. Стиль кода

- Используй constructor injection; field injection запрещён.
- Предпочитай небольшие классы с одной ответственностью и явные имена предметной области.
- Для неизменяемых value objects и конфигурации используй `record`, когда это уместно.
- Не используй `null` как неявное состояние, если состояние можно выразить типом или явным результатом.
- Не перехватывай `Exception` без преобразования, журналирования или осмысленного восстановления.
- Комментарии объясняют причину решения, а не повторяют код.
- Не выполняй массовый рефакторинг и обновление зависимостей попутно с небольшой функциональной задачей.

## 9. Тесты и проверка изменений

Новые тесты для уже реализованных security invariants и regression-critical сценариев пишутся на существующем стеке JUnit/Testcontainers. Для PostgreSQL locking/concurrency semantics H2 не использовать. В остальных модулях тестовую инфраструктуру не расширяй до отдельного решения команды без прямой задачи. Существующие тесты не удаляй и не переписывай без прямой задачи.

Минимальная проверка изменений без запуска тестов:

```bash
./gradlew classes
```

Для проверки сборки исполняемого JAR:

```bash
./gradlew bootJar -x test
```

Обе команды требуют подготовленного API-контракта в `../tovarika-api-contract/dist` либо пути из `TOVARIKA_API_CONTRACT_DIR`.

## 10. Локальный запуск и Docker

- `./gradlew bootRun` запускает приложение локально; Spring Boot поднимает инфраструктуру из Compose.
- `docker compose up --wait` запускает только PostgreSQL и MinIO.
- `docker compose --profile full up --build --wait` запускает весь стек вместе с приложением.
- Не убирай профиль `full` у сервиса `app`: он предотвращает рекурсивный запуск приложения при `bootRun`.
- Docker build context должен включать каталоги `Tovarika` и `tovarika-api-contract` на одном уровне.

## 11. Порядок работы

1. Перед реализацией найди соответствующий endpoint и модели в API-контракте.
2. Определи владельца функциональности и не создавай обходных зависимостей между модулями.
3. При изменении данных сначала добавь миграцию, затем persistence и прикладную логику.
4. Вноси минимальный связный diff и не редактируй сгенерированные файлы.
5. Проверь компиляцию или сборку JAR без тестов и сообщи о непроверенных частях.
6. При изменении структуры, интеграций или команд обнови `overview.json`, `RULES.md` и при необходимости `README.md`.
