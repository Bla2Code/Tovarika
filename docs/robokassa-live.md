# Реальная оплата Robokassa

В `LIVE` покупка доступна всем авторизованным пользователям. После подписанного
серверного подтверждения начисляются Товарики и появляется запись «Покупка пакета»
в «Истории использования». Повторное подтверждение не создаёт второе начисление.

## Файлы, которые нужно добавить вручную

В каталоге развертывания `/home/deploy/tovarika-backend` создайте два файла:

| Файл на сервере | Содержимое | Переменная для другого пути |
| --- | --- | --- |
| `secrets/live_robokassa_pass1` | Рабочий пароль № 1 магазина Robokassa | `ROBOKASSA_LIVE_PASSWORD1_SOURCE` |
| `secrets/live_robokassa_pass2` | Рабочий пароль № 2 магазина Robokassa | `ROBOKASSA_LIVE_PASSWORD2_SOURCE` |

В каждом файле должно находиться только значение соответствующего пароля, без
названия переменной, кавычек и пробелов вокруг значения. Введите его в редакторе,
не вставляйте пароль в командную строку, Git или переписку. Файлы в репозитории
не созданы; deployment не загружает эти пароли автоматически.

Файлы должны читаться пользователем контейнера (`APP_UID` / `APP_GID`), например
при принадлежности этому пользователю и правах `600`. Рабочие пароли должны
отличаться от соответствующих тестовых: приложение не разрешает `LIVE` с
совпадающими наборами. Логин магазина — `ROBOKASSA_MERCHANT_LOGIN`, по умолчанию
`tovarika`.

Production Compose разрешает эти пути относительно своего файла. При штатном
deployment это абсолютные пути:

- `/home/deploy/tovarika-backend/secrets/live_robokassa_pass1`;
- `/home/deploy/tovarika-backend/secrets/live_robokassa_pass2`.

Для локального `compose.yaml` пути по умолчанию —
`../.secrets/live_robokassa_pass1` и `../.secrets/live_robokassa_pass2` относительно
корня репозитория. Оба Compose монтируют и тестовые, и рабочие файлы; они должны
существовать до запуска `app`. Для локального `TEST` рабочие файлы могут быть
пустыми, но реальные платежи потребуют оба непустых рабочих пароля.

Существующие `test_robokassa_pass1` и `test_robokassa_pass2` остаются на своих
местах. Их не нужно заменять рабочими паролями.

## Настройки и запуск

1. В технических настройках магазина Robokassa проверьте рабочие пароли,
   логин магазина, алгоритм подписи `SHA256` и адреса:

   | Поле | URL | Метод |
   | --- | --- | --- |
   | Result URL | `https://tovarika.com/api/v1/billing/robokassa/result` | POST |
   | Success URL | `https://tovarika.com/api/v1/billing/robokassa/success` | GET |
   | Fail URL | `https://tovarika.com/api/v1/billing/robokassa/fail` | GET |

2. Добавьте два рабочих файла на сервер до развертывания новой версии.
3. Production Compose уже использует `ROBOKASSA_MODE=live` по умолчанию.
   Если ранее явно задано `ROBOKASSA_MODE=test` или `disabled`, измените его на
   `live`: явная настройка имеет приоритет над значением по умолчанию.
   Локальный Compose по умолчанию остаётся в `TEST`; для реальной оплаты
   задайте `ROBOKASSA_MODE=live`.
4. Разверните новую версию обычным способом. В общем репозитории
   `tovarika-api-contract` также нужна версия с поддержкой обоих значений
   `testMode` (снято прежнее ограничение `const: true`); публикуйте её до сборки
   backend. Миграция `081-robokassa-live` разрешает реальные заказы,
   `082-robokassa-receipt` добавляет сохранение состава чека для новых покупок.
   Существующие заказы, баланс и история не пересчитываются. Для уже развернутой
   новой версии после добавления или замены
   файлов пересоздайте контейнер приложения из каталога deployment:

   ```sh
   docker compose -f docker-compose.prod.yml up -d --force-recreate app
   ```

При отсутствии рабочих паролей приложение не переключается на тестовую оплату.
Если файл отсутствует, Compose не сможет смонтировать secret; если файл пустой,
создание оплат будет недоступно. Режим существующего заказа сохраняется, включая
повтор запроса с тем же `Idempotency-Key`. Обработчик Result URL выбирает пароль
по заказу, поэтому смена глобального режима не меняет проверку старых платежей.

## Проверка после развертывания

1. Авторизуйтесь обычным пользователем, не включённым в тестовый список.
2. Выберите пакет. На форме Robokassa должна открыться реальная оплата
   (`IsTest=0`). Проверьте, что в составе заказа есть название пакета и полная
   цена, и запишите исходный баланс. Используйте новый заказ, созданный после
   обновления: старые ссылки не получают новый состав чека.
3. Выполните контролируемую реальную покупку. После серверного подтверждения
   проверьте прибавку Товариков, срок пакета и одну запись «Покупка пакета»
   в «Истории использования».
4. Обновите страницу: баланс и число записей не должны увеличиться повторно.
5. Проверьте автоматическую регистрацию чека в подключённом «Мой налог» и его
   получение покупателем. Наличие `Receipt` в запросе означает передачу состава,
   а не подтверждение успешной регистрации: результат проверяется у Robokassa.

## Автоматический чек для самозанятого на НПД

В кабинете Robokassa должно быть подключено автоматическое формирование чеков
через «Мой налог». Backend передаёт номенклатуру в `Receipt` при открытии оплаты;
Robokassa регистрирует чек по подключённой схеме и отправляет его покупателю.
Email покупателя собирается на стороне платёжной формы Robokassa; новых полей
в интерфейсе Товарики нет.

Для каждого нового заказа сохраняется неизменяемый JSON с одной позицией:

```json
{"items":[{"name":"Доступ к сервису Товарика: пакет 140 Товариков на 1 месяц","quantity":1,"sum":990.00,"tax":"none"}]}
```

Количество — один пакет, сумма — полная цена из заказа в рублях, `tax=none` — без
НДС. `sno` не передаётся: НПД определяется настройками магазина и отсутствует
среди поддерживаемых значений этого поля. Необязательные признаки ККТ
`payment_method` и `payment_object` не задаются для этой схемы НПД.

`Receipt` кодируется UTF-8 и URL-encoding до включения в SHA256-подпись перед
рабочим или тестовым паролем № 1. Затем параметры целиком кодируются в URL;
поэтому в готовой ссылке начало `Receipt=%257B` ожидаемо. Это соответствует
[официальному SDK Robokassa](https://github.com/robokassa/sdk-node/blob/main/src/services/payment.ts).
Для одной позиции сохраняется существующий переход по GET-ссылке; API и UI
покупки не меняются. Большие корзины потребуют POST-формы.

Повторный запрос с тем же `Idempotency-Key` использует сохранённый состав,
включая название и сумму. В существующих заказах поле `receipt_json` остаётся
`NULL`: миграция не дописывает номенклатуру и не изменяет уже выданные платежные
параметры. Чек по уже оплаченному заказу № 17 этим обновлением задним числом
не создаётся; его нужно разобрать отдельно по ответу поддержки и уведомлению
Robokassa. Метод отложенной регистрации `Receipt/Register` для НПД не применяется.

Возврат браузера сам по себе не начисляет Товарики: подтверждение приходит
серверным запросом на Result URL. Подпись этого уведомления по паролю № 2
не меняется при добавлении `Receipt`; состав чека не входит в неё.

Документация Robokassa: [тестовый и основной режимы](https://docs.robokassa.ru/ru/testing-mode),
[серверное подтверждение](https://docs.robokassa.ru/ru/notifications-and-redirects),
[состав чека](https://docs.robokassa.ru/ru/fiscalization),
[ограничения отложенной регистрации](https://docs.robokassa.ru/ru/deferred-receipt-registration).
