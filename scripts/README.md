# Скрипты

## Ручное начисление Товариков

`grant-credits.sql` начисляет произвольную положительную сумму существующему активному
пользователю по email. Запускать через PostgreSQL-клиент `psql` в отдельном подключении.
Нужна база с примененными миграциями, включая `080-credit-packages`.

Локально или на сервере с установленным `psql` (подставьте свои параметры подключения):

```sh
psql -X -h <DB_HOST> -p <DB_PORT> -U <DB_USER> -d <DB_NAME> \
  -v email='client@example.com' -v amount='25.50' \
  -v reason='Компенсация за неудачный результат' \
  -f scripts/grant-credits.sql
```

Если PostgreSQL работает в Docker, `psql` можно запустить внутри его контейнера:

```sh
docker exec -i <POSTGRES_CONTAINER> psql -X -U <DB_USER> -d <DB_NAME> \
  -v email='client@example.com' -v amount='25.50' \
  -v reason='Компенсация за неудачный результат' \
  < scripts/grant-credits.sql
```

Email ищется без учета регистра, внешние пробелы удаляются. `amount` задается **в Товариках**,
а не во внутренних units: `25.50` = 25,5 Т = 2550 units. Разделитель — точка; разрешено
не более двух знаков после нее. `reason` необязателен, по умолчанию `Manual credit grant`;
при передаче причины используйте от 1 до 210 символов без секретов и содержимого пользовательских файлов.
Параметры подключения передаются штатными средствами PostgreSQL; скрипт не читает `.env`
и источники Compose secrets. Не включайте пароль в команду или connection URL.

Каждый успешный запуск — **новое начисление**, в том числе при повторе той же команды.
После `COMMIT` скрипт выводит сумму, email и ID проводки. При ошибке `psql` завершится
с ненулевым кодом, а транзакция откатится. Если соединение оборвалось и результат неизвестен,
перед повтором проверьте историю: автоматической защиты от повторного начисления нет.

Товарики бессрочные и доступны для расходования; «Всего использовано» и активные резервы
не меняются. В истории используется существующий тип `trial_grant` с его текущей подписью
на фронтенде. Причина сохраняется в `billing_ledger.reference` с префиксом `manual:` и
не выводится пользователю. Платеж/покупка не создается, учет первоначального бесплатного
начисления (`billing_trial_grants`) не меняется. Бессрочные начисления не входят в список
купленных пакетов `/billing/credit-lots`.

Если активный пользователь не найден, найдено несколько активных аккаунтов с этим email,
кошелек не инициализирован, сумма некорректна или баланс превысит допустимый максимум,
начисление не выполняется. Для пользователя без кошелька сначала нужен вход в приложение
и открытие баланса. Блокировки согласованы с backend; ожидание блокировки ограничено 10 секундами.
Истечение ранее купленных пакетов продолжает обрабатываться штатным backend.

## Сценарии карточек

Этот каталог не публикует template assets в MinIO. `seed-card-variants.py` готовит
только неизменяемые Liquibase-миграции; загрузку reference-файлов выполняет
`template-assets-init` при backend-деплое.

По умолчанию источник — `assets/templates/tpl_fashion_hero/card-variants.json`.
Для другого шаблона передайте `--source`. Проверка без записи:

```sh
python3 scripts/seed-card-variants.py --check
python3 scripts/seed-card-variants.py --source assets/templates/tpl_fashion_accent/card-variants.json --check
```

Для нового набора изменений выберите следующий свободный номер миграции:

```sh
python3 scripts/seed-card-variants.py --source assets/templates/tpl_fashion_accent/card-variants.json --output src/main/resources/db/changelog/changes/NNN-fashion-card-variants.yaml
```

Скрипт требует новый файл; существующий файл, в том числе опубликованный в HEAD,
не перезаписывается. Подключите созданный файл в конце master changelog, затем
выполните `.agent/rules/check-liquibase-migrations.sh` и `./gradlew test`.
Liquibase загружает данные атомарно при штатном запуске. Скрипт не подключается
к БД и не читает credentials. `013` — первоначальный seed ровно десяти сценариев;
обновление JSON требует отдельной новой data migration. Reference и общий recipe
сохраняются; уже начатые серии и поставленные в очередь Card используют snapshots.
